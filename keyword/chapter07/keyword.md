 데이터의 정확성이 중요해 결함이 치명적인 경우 

- **송금 및 결제:** 돈이 오가는 상황에서 보내기 완료라고 먼저 띄웠는데 실제로는 잔액 부족으로 실패한다면 시스템 신뢰도 붕괴.
- **중요 자산 삭제:** 파일이 삭제되었습니다라고 표시했는데 서버 오류로 남아있다면, 보안상 큰 위협

서버의 비즈니스 로직이 복잡할 때

- 단순 수정이 아니라 서버에서 복잡한 검증을 거쳐야 하거나, 서버에서 생성되는 데이터(예: 서버에서 할당하는 ID, 자동 계산된 최종 금액)가 UI에 즉시 반영되어야 하는 경우

실패 확률이 높은 작업

- 동시성 제어가 엄격한 작업(예: 수강신청, 선착순 티켓 예매)은 낙관적으로 처리했다가 뒤늦게  실패했습니다 라고 롤백하는 과정이 사용자에게 불만을 유발

롤백(Rollback) 비용이 클 때

- 낙관적 업데이트 후 사용자가 연쇄적으로 다음 행동을 취해야 한다면, 첫 번째 작업이 실패했을 때 그 뒤의 행동을 어떻게 되돌릴 것인지에 대한 로직 복잡

- **낙관적 업데이트(OptimisticUpdate)**를 왜 도입해야 하는지, 이 패턴이 해결하려는 문제를 실제 서비스 맥락에서 설명해보세요.
    
    해결하려는 문제: 네트워크 문제 및 지연으로 인한 사용자 경험저하
    
    일반적으로 데이터 변경 요청시 요청 → 서버 처리 → 응답 수신 → UI 갱신의 과정을 거침
    이때 네트워크가 느리거나 서버 부하가 있으면 버튼을 눌러도 반응이 없는 현상이 발생합니다. 사용자는 버튼이 제대로 눌렸는지 의심하며 중복 클릭을 하거나, 서비스가 느리다는 부정적인 인상을 받음
    
    실제 서비스 맥락
    
    - 즉각적인 피드백: 좋아요 버튼이나 할 일 체크박스처럼 빈번하게 일어나는 상호작용에서 사용자에게 실시간성을 제공
    - 체감 성능 향상: 서버 속도는 동일하더라도, 사용자는 서비스가 빠르게도 체감하게 됨
- TanStack Query 기반 구현 흐름을 `onMutate → (mutate) → onError → onSettled` 순서로 기술해주세요..
    1. **onMutate** 
        - 실제 API 호출이 시작되기 전에 호출
        - 새로운 데이터를 반영하기 위해 관련 쿼리를 `cancelQueries`로 중단시켜 이전 데이터가 덮어씌워지는 것을 방지
        - `getQueryData`로 현재 캐시 값을 스냅샷으로 저장
        - `setQueryData`를 사용해 캐시를 새로운 데이터로 즉시 업데이트
        - 스냅샷 데이터를 `context`로 반환
    2. **(mutate)**
        - 실제 서버로 네트워크 요청
    3. **onError** 
        - 서버 요청이 실패했을 때 실행
        - `onMutate`에서 반환했던 스냅샷(context)으로 캐시를 이전 상태로 롤백
    4. **onSettled** 
        - 성공/실패 여부와 상관없이 마지막에 실행
        - `invalidateQueries`를 호출해 서버의 실제 데이터와 캐시를 동기화하여 로컬 데이터의 정합성 확인
- ToDo “생성” 및 “좋아요 토글”에 **낙관적 업데이트(OptimisticUpdate)**를 적용했을 때의 **실패/충돌 롤백 전략**을 설계해주세요.
    
    ToDo 생성은 서버에서 id를 할당하기전에 업데이트 가능해야함
    
    - **설계 전략:**
        - **임시 ID 사용:** `onMutate`에서 `Date.now()`나 UUID를 이용해 임시 ID를 부여해  UI에 노출, 
        이때 저장 중...과 같은 처리알림으로 사용자에게 상태를 알려 혼동을 방지
        - **실패 롤백:** `onError`에서 임시 ID가 포함된 배열에서 해당 항목만 `filter`하여 제거.
        - **성공 처리:** `onSettled`에서 캐시를 무효화하여 서버가 할당한 실제 ID로 교체
    
    좋아요는 이전 상태에 의존하며, 여러 사용자 동시에 조작 시 충돌 가능성 농후.
    
    - **설계 전략:**
        - **스냅샷 기반 복구:** `onMutate` 시 해당 게시글의 `likeCount`와 `isLiked` 상태를 저장
        - **충돌 방지:** 이전 Mutation이 진행 중이라면 새 요청의 `onMutate`에서 기존 쿼리를 취소하여 데이터 충돌 방지.
        - **롤백 로직:** 서버 에러 발생 등으로 실패 시, `onMutate`에서 저장한 과거 스냅샷으로 덮어씌움.

        **Q3 답변.**
        
        ### (a)
        
        네트워크 불안정 상황과 흐름이 중요할때 강점
        
        - **흐름의 유지:** 사용자는 여러개의 할일을 연속 체크 가능, 매번 1~2초씩 기다려야 한다면 앱 이탈 가능성 커짐.
        - **오프라인 사용성:** 잠시 연결이 끊겨도 내 동작이 수행됐다는 피드백을 줌, 나중에 연결될 때 앱이 알아서 처리한다면 사용성이 크게 증대됨.
        
        ### (b)
        
        서버가 끝내 실패를 알리면, UI는 롤백이 되어야 함
        
        - **햅틱:** 사용자는 요청 이후 다른곳에 시선이 가게됨. 이때 요청이 실패 했다면 진동 (햅틱)을 주어, 이전 요청이 처리가 안됐다는 것 알려야함.
        
        ### (c)
        
        1. **서버 생성 ID:** 메모 작성의 경우, 서버가 생성한 ID를 사용하지 않고 가짜 ID로 처리했다가 실제 ID와 충돌하여 데이터가 꼬일 수 있음
        2. **데이터 무결성:** 친구 수락은 나뿐만 아니라 상대방의 목록에도 반영되야함. 낙관적으로 수락했는데 서버 오류로 수락이 안 되었다면, 상대방에게는 친구로 뜨고 나에게는 안 뜨는 등 데이터 불일치가 발생할 수 있음
        3. **예측 어려움:** 한 번의 클릭으로 여러 곳(친구 목록, 안 읽은 메시지 수, 알람 로그)이 동시에 바뀌어야 하는 액션을 모두 예측해서 미리 보여주기가 어려움
